# GnuCOBOL file organization vs Java conversion (ACME Bank v3)

## The conflict

### COBOL source (production / mainframe)

```cobol
       SELECT LOAN-FILE
           ASSIGN TO "LOANFILE.dat"
           ORGANIZATION IS INDEXED
           ACCESS MODE IS SEQUENTIAL
           RECORD KEY IS LOAN-ID
```

`ASSIGN TO "LOANFILE.dat"` is a **relative path** resolved from the process **current working directory** when the program runs.

### Fixture data in this repo

Under `acme-bank-v3/` and `acme-bank-v3/data/` we store **flat fixed-width** `.dat` files (generated by `scripts/generate_data.py`). They are **not** Berkeley DB indexed files.

### Generated Java

The modernization pipeline treats these as **flat sequential byte streams**: `BufferedReader`, fixed record lengths, substring parsing. This matches the on-disk layout and works without any indexed-file runtime.

### GnuCOBOL behavior

| Topic | Behavior |
|--------|----------|
| Missing file in CWD | `OPEN` fails if `LOANFILE.dat` is not in the run directory |
| `ORGANIZATION IS INDEXED` | Expects Berkeley DB format (typically `.dat` + `.idx` pairs), **not** our flat fixtures |
| `ACCESS MODE IS RANDOM` / `DYNAMIC` | Requires indexed organization and record keys |
| `START ... KEY` | Indexed-only; invalid for true sequential files |

**Result:** Java runs fine on flat `.dat` files; GnuCOBOL with the **original** INDEXED programs fails or misreads the same files.

## Solution options

| Option | Description | Use case |
|--------|-------------|----------|
| **A — SEQUENTIAL variant (recommended for baseline)** | Rewrite FILE-CONTROL to `ORGANIZATION IS SEQUENTIAL`, drop keys, map `INVALID KEY` → `AT END`, remove `START` | Behavioral baseline / batch smoke tests on flat `.dat` |
| **B — Build indexed files** | Python/cob tool builds GnuCOBOL-compatible indexed datasets from flat `.dat` | True equivalence testing with alternate keys |
| **C — Compiler flags** | e.g. `cobc -fno-indexed-key` (version-dependent) | Environment-specific; not portable |

**Production** deployments keep **INDEXED** sources; the mainframe runtime provides real indexed files.

**Baseline testing** uses **SEQUENTIAL** variants under `src/sequential/`.

## SEQUENTIAL variant transforms

Implemented in `cobol-modernization-service/app/services/cobol_sequential_variant.py`:

1. `ORGANIZATION IS INDEXED` → `ORGANIZATION IS SEQUENTIAL`
2. `ACCESS MODE IS RANDOM` / `DYNAMIC` → `ACCESS MODE IS SEQUENTIAL`
3. Remove `RECORD KEY` and `ALTERNATE RECORD KEY` (including `WITH DUPLICATES`)
4. `INVALID KEY` → `AT END`; `NOT INVALID KEY` → `NOT AT END`
5. Remove `START` statements (comment marker left in source)

**Trade-off:** Alternate-key lookups and `START`/`READ NEXT` positioned reads are not exercised in baseline runs. Batch programs that scan files sequentially (e.g. LOANEVAL loan master loop) remain testable.

## Pipeline: baseline test mode

Enable for behavioral COBOL↔Java diff runs:

```bash
# Environment (API / behavioral diff)
export BEHAVIORAL_BASELINE_TEST_MODE=1
```

Or per request:

```json
{
  "baseline_test_mode": true,
  "cobol_source": "...",
  "program_name": "LOANEVAL"
}
```

When enabled:

1. **COBOL source** — Uses `acme-bank-v3/src/sequential/<PROGRAM>.cbl` when present, otherwise applies an inline `create_sequential_variant()` transform.
2. **Data files** — Copies required `ASSIGN` `.dat` files from `acme-bank-v3/` / `data/` into the behavioral run working directory (same CWD as `program.exe`).

See `app/services/behavioral_baseline.py` and `app/services/behavioral_file_harness.py`.

## Quick verification

```bash
cd cobol-modernization-service
python scripts/create_sequential_variants.py
python -m pytest tests/test_cobol_sequential_variant.py -v
```

Compile a baseline variant (from repo root, with data files in CWD):

```bash
cd acme-bank-v3
cp data/*.dat .
cobc -x -o loaneval_seq src/sequential/LOANEVAL.cbl
./loaneval_seq
```
